# M3 — Rules, policy files, timeouts, approval queue

**Status:** done 2026-09-12.

**Goal:** routine prompts resolve themselves by rules you wrote, dangerous ones are refused or always reach you, nothing waits forever unless you want it to, and every pending approval across all sessions is one keyboard-driven list.

**Exit criteria**

- A deny rule refuses a matching request without showing a card; an allow rule approves it; both appear in the session history with the rule and the file it came from.
- An ask rule always reaches a person and hides every "always allow" option for that request.
- "Always allow" can save a rule into the project's Loom policy, editable before saving.
- A repo's committed allow rules do nothing until someone on this hub trusts them; deny and ask rules apply immediately.
- A session, project, or hub can set an approval timeout that denies when it runs out; the card shows the countdown.
- One approvals list across sessions, answerable with the keyboard.
- The policy for a project and for the hub can be viewed and edited in the client, with rule errors shown.

## Design decisions

- **Rule syntax is Claude Code's** (`Tool`, `Tool(specifier)`), so one grammar serves both. Loom implements a subset and **errs toward asking**: where Loom's reading of a command or path is uncertain, allow rules do not match and deny and ask rules do.
- **Precedence:** deny, then ask, then allow, across hub and project policy together.
- **Policy files:** hub `policy.json` next to `hub.json`; project `<root>/.loom/policy.json`, where root is the nearest ancestor of the session's directory with a `.loom` folder, else a `.git` folder, else the directory itself.
- **Trust:** the hub records a hash of each project's allow list in its data directory. Allow rules from an untrusted list are ignored and reported. Saving a policy from the client or saving a rule from an approval trusts the result, because a person on this hub wrote it.
- **Rules only judge permission prompts.** Clarifying questions always go to a person.
- **Timeout order:** session spec, then project policy, then hub policy, then none. Only `deny` is a timeout action until the Steward exists.
- **Rule decisions are logged as a request and its resolution** with resolver `rule`, so the audit trail shows them like any other.

## Verified with real Claude in the browser (2026-09-12)

One chat session in a demo project with a hub policy (`deny: Bash(rm *)`, `ask: Bash(git push *)`) and a committed, untrusted project policy (`allow: Bash(node *)`):

- `rm -f scratch.txt` was denied by the hub rule with no card; history read "Denied by rule Bash(rm *) · hub policy", and Claude's reply quoted the rule.
- `node -e …` reached a card because the project allow rule was untrusted; the session showed the trust banner and the Policy button was highlighted. Trusting from the policy editor recorded the hash.
- "Always allow…" prefilled Claude Code's own suggestion; after editing it to `Bash(node -e *)` and saving, the rule appeared in `.loom/policy.json` and trust followed the new hash.
- `git push origin main` showed "Always asks: Bash(git push *) in hub policy" with no always-allow option, and was denied from the approvals panel with the `d` key.
- A one-minute timeout set in the policy editor showed "denies in 0:59" on the card, then denied; the command never ran.

## Found and fixed during verification

- Pasting a new token link into an open tab changed only the URL hash, so the client kept the old token and showed "refused". The client now listens for hash changes.
