# M11 — Relay

**Goal:** reach the work hub from home when SSH and Tailscale are blocked, through a relay on `furevikstrand.cloud`, without the relay being able to read or change anything.

**Exit criteria**

- A hub with `relay` in `hub.json` dials out to the relay and keeps that connection up with reconnects. Nothing inbound is needed on the hub's machine.
- Browsers and phones open `https://<hub name>.<relay domain>` and use the hub exactly as over any other address: client, WebSocket, PWA install, push.
- TLS runs end to end between the browser and the hub. The relay routes on the TLS server name and forwards ciphertext; it never holds a certificate or key for a hub's name.
- The hub gets and renews its certificate from Let's Encrypt itself (HTTP-01 through the relay), or uses certificate files.
- The relay admits only hubs enrolled on it (`loom-relay add-hub`), caps connections and streams, and times out idle and half-open connections.
- The relay is one bundled file with a systemd unit and deploy notes, including running behind an existing nginx on 443.

## Design decisions

- **TLS passthrough, not an application-level seal** (ADR-0014). Standard TLS gives the end-to-end property v1's draft built from Noise, with no Loom crypto. The relay reads the ClientHello's server name, nothing more.
- **Dial-back streams.** The hub keeps one control WebSocket to the relay. For each visitor, the relay asks the hub to open a data connection (an HTTP upgrade on the relay's own TLS endpoint), then splices visitor and hub bytes together, starting with the ClientHello it already read.
- **The relay has its own name and certificate** (the relay domain itself, e.g. `relay.furevikstrand.cloud`) for the control and data endpoints, obtained on the VPS the usual way (certbot or Caddy). Hub names are subdomains of it, so DNS is one record for the relay and one wildcard.
- **Port 80 only for ACME.** Plain HTTP to a hub name is forwarded only for `/.well-known/acme-challenge/`; everything else redirects to https.
- **Enrollment secrets** are per hub, shown once by `add-hub`, stored hashed on the relay. They stop strangers from using the relay; they protect no data, which TLS does.
- **Addresses:** the hub sees the relay's address on the socket, so the relay passes the visitor's address in the stream request, and the hub uses it for the login limit. Hooks never work through the relay.

## Verification (2026-09-13)

- Tests: 322 passing, 2 skipped (live SDK). New:
  - Relay units: the server name from real Node ClientHellos, arriving in pieces or split across records; non-TLS input; HTTP heads; the registry storing hashes only, 0600, replacing secrets, and picking up changes made by another process.
  - End to end (`hub/test/relay.test.ts`, throwaway CA): relay, hub, and clients on this machine. `https` and `wss` reached the hub through the relay with the hub's own certificate (checked by the peer certificate name); the hub token signed in; `/hooks` answered 403 through the relay; the relay's own name answered "Loom relay"; unknown names and foreign names got the connection closed; port 80 carried an ACME challenge to the hub, 404 for an unknown token, and redirected other paths; after the relay closed and started again on the same ports, the hub reconnected and traffic flowed. An unenrolled hub was refused with a clear reason.
  - Certificate files: used for the relay name, refused for another name.
- ACME for real, with Pebble v2.10.1 and `pebble-challtestsrv` as DNS: relay run from its CLI on 8443 and 5002 with its own test CA certificate, hub enrolled with `add-hub`, hub started with the printed block (URL corrected to include the port; `add-hub` now prints non-default ports). The hub logged `relay up`, requested a certificate, Pebble validated HTTP-01 from three perspectives through the relay's port 80 path, and the certificate was stored with the account URL printed for CAA. After restarting the relay, the hub reconnected in 2 s and `curl --cacert <Pebble root>` to `https://work.relay.localhost:8443/loom.json` returned 200 with a verified chain; an unknown name got an immediate close.
- Found and fixed on the way:
  - TLS servers ignored ClientHello bytes put back with `unshift` (handshakes hung); streams are now wrapped in a JS Duplex that replays them.
  - Visitor addresses were lost behind the wrapper (`_parent` is not the wrapped stream); each connection now gets its own server object that tags its requests.
  - Double `pipeline()` splicing leaked listeners (MaxListenersExceeded on the relay).
  - An empty reason in "relay down" for connection-refused, and the enrollment refusal message being overwritten.
