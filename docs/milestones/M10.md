# M10 — PWA on the phone, with web push

**Goal:** approve from the couch. Install Loom on a phone from the hub's own page, get a notification when something waits for you, and decide it there.

**Exit criteria**

- The client is an installable PWA: manifest, icons, service worker, standalone display, usable at phone width (rail as a drawer, approvals first).
- A hub sends web push for approvals that still wait for a person after a short delay (default 15 s), so a phone stays quiet while you handle things at the desk. Notifications never include tool input beyond the one-line summary.
- Tapping a notification opens the approvals panel on that approval. Always-ask approvals still need the full card.
- "Connect a phone" in the client shows a QR code with the phone address and token.
- HTTPS for phones without custom crypto: `tailscale serve` in front of the hub (documented), or the hub's own TLS listener from certificate files (`tls` in `hub.json`), for example from `tailscale cert`.
- Behind a local proxy, the hub uses `X-Forwarded-For` for the login limit and refuses `/hooks` for forwarded requests.

## Design decisions

- **Push encryption comes from `web-push`** (RFC 8291 and VAPID), not from Loom code. VAPID keys are made on first use and kept in the hub's data folder, readable only by the user.
- **One pushing hub per installed app.** A browser push subscription is bound to one server key, so the hub serving the PWA is the one that pushes. Other hubs in the same client still work, without push.
- **Subscriptions are hub files, not events** (`push.json`, like `trust.json`): they are device settings, not session history. Expired ones (404 or 410 from the push service) are removed.
- **Delay before pushing** so a desk session does not buzz the phone: an approval resolved within `push.delaySeconds` never pushes.
- **The token travels by QR code** from a screen that already has it. Per-device tokens are left for later; losing the phone means `--new-token`.

## Verification (2026-09-13)

- Tests: 314 passing, 2 skipped (live SDK). New: web push through `web-push` to a test device that decrypts the payload with its own keys (aes128gcm, VAPID header), persistence and 0600 key file, removal of devices on 404/410, https-only endpoints; the notifier's delay, cancel on resolve, waiting for the Steward, question wording and clipping, no tool input in payloads; `X-Forwarded-For` and forwarded-request detection, TLS bind planning, a TLS listener next to plain loopback, hooks refused through a proxy; the service worker's push and click handlers in a VM; phone-ready helpers.
- Real hub on 7421 with `push.delaySeconds: 5`, trusting a local HTTPS fake push service through `NODE_EXTRA_CA_CERTS`:
  - A fake device registered with `push.subscribe`; `push.test` arrived decrypted, VAPID-signed, TTL 3600, urgency high.
  - A Haiku session asked to `touch` a file (a few cents). The approval appeared after 3 s and the push arrived 5 s later: "Wade needs approval: Run: touch …", tag `approval-<id>`, url `/#approval=<id>`.
- Browser at Pixel 7 size (412×915) against that hub: service worker active, manifest loaded; the top bar showed "Need you 1"; opening `/#approval=<id>` showed the approvals panel full screen on that approval; tapping **Allow** ran the command. The drawer opened from ☰ and closed on choosing a session. **Phone and notifications…** listed the fake device, drew a QR code for the phone address, and **Turn on** explained that this browser has no push service ("push service not available" is what automation Chromium reports).
- Found and fixed on the way: the approvals panel had no way to close on a phone (no Escape key, no margin to tap); it has a Close button now and hides keyboard hints at phone width.
