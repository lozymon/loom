# M6 — The Cockpit and the `loom` tools

**Status:** done 2026-09-12.

**Goal:** tell the Cockpit to run a mission, and let sessions coordinate with each other, without giving any agent more authority than it should have.

**Exit criteria**

- One Cockpit per hub, started by a person, pinned at the top of the rail.
- The Cockpit can list, read, start, message, wait for, interrupt, and stop sessions, work the board, and set levels within the hub maximum.
- On a hub where models may approve (`stewardModel` on), the Cockpit can decide other sessions' approvals and answer their questions; never its own, never ask-rule matches, never on the work hub.
- Every Claude session gets `loom` tools for coordination: see other sessions, read them, message them, shared notes, file claims, and adding cards.
- Terminal sessions get a `loom` command on their PATH with the same abilities.
- Messages between sessions are labeled as coming from a session or the Cockpit, never as the developer.

## Design decisions

- **Session tokens, not the hub token.** Each engine launch gets a token that identifies its session and role (`session` or `cockpit`). The hub checks every command against the caller's role in one place. Humans keep the hub token.
- **One tool definition, two transports.** Chat sessions get the tools in the hub process through the Agent SDK. Claude terminals get a stdio MCP server, and terminals get the `loom` CLI; both talk to the hub over WebSocket with the session token.
- **`loom` tools run without permission prompts** (`mcp__loom__*` is allowed for Loom's own sessions), because the hub authorizes each call by role. Everything they cause, such as a started session's own tool calls, still goes through approvals.
- **Model approvals follow the hub's rule.** The Cockpit may decide approvals only where the Steward's model stage is allowed.
- **Notes and claims are in memory,** per project, like v1: coordination state, not history.
- **The Cockpit's own directory** is in the hub data folder; it works on projects through tools and sessions, not by editing files itself.

## Verified with real models (2026-09-12)

On a hub configured like the work hub (Steward off, maximum level accept-edits):

- **Mission:** the Cockpit (Opus 5) was asked to start two sessions on Haiku at accept-edits, on worktree branches, each making a change and saving a note, then to wait and report. It called `start_session` twice, `wait_for` twice, and `notes`; both workers set their notes with their own loom tools; the report was accurate and mentioned the branches were not merged.
- **Limits:** asked to approve a pending request and set a session to Full, the Cockpit called `pending_approvals` and `decide_approval`, the hub refused ("on this hub only a person may decide approvals"), and the Cockpit reported both as waiting for a person. The approval stayed pending and the level unchanged.
- **Terminal CLI:** inside a terminal session, `loom notes`, `loom claim`, `loom claims`, and `loom send` worked; the receiving session saw the message labeled as from another session; a Cockpit-only command was refused.

## Found and fixed during verification

- **Every prompt blocked:** Loom v1's hooks in the user's Claude settings ran `loom hook prompt`, which reached v2's `loom` and exited 2, the hook code for "block". v2's CLI now ignores `hook` and never exits 2.
- **Tools deferred:** Claude Code deferred the loom tools behind tool search, and a v1 `loom-commands` skill sent the Cockpit looking for a CLI with Bash. The tools are now always loaded and the Cockpit is told to ignore v1 material.
- **No tools at all:** `answer_question` used `z.record`, which made MCP tool listing fail and hid every loom tool. Replaced with a list, with a listing test for both roles.
- **Debugging:** `LOOM_DEBUG_SDK=1` logs raw SDK messages; it is how the first problem was found.
