# M4 — Many sessions: worktrees, overview, board

**Status:** done 2026-09-12.

**Goal:** run five sessions on five cards in parallel without them stepping on each other, and see all of it on one screen.

**Exit criteria**

- A session can start in its own git worktree on a new branch; the rail shows the branch.
- Sessions group by project in the rail; they can be renamed and archived, and archiving can remove a clean worktree.
- An overview shows every session with its state, latest activity, pending approvals, and cost, plus cost today.
- Each project has a board in `.loom/board.json`: add, edit, move, and remove cards; dispatch a card into a session; card status follows its session.
- "Run" keeps up to N cards running from the to-do lane.
- Loom policy files cannot be edited by an agent without a person's approval.

## Design decisions

- **Worktrees live in the hub's data directory**, `worktrees/<repo>-<hash>/<branch>`, not inside the repository, so tools that walk the repo do not see nested checkouts.
- **Loom never deletes branches.** Archiving can remove a worktree directory only if it has no uncommitted changes, unless the person forces it.
- **A worktree belongs to its main repository.** Policy, trust, and the board are read from the main repository's root, so a branch checkout cannot change the rules or lose trust.
- **Board cards are project files** (`.loom/board.json`), committable like v1. The hub is the only writer while running and re-reads the file when it changes on disk.
- **Card lanes:** to do, running, review, done, failed. A dispatched card is running; when its session finishes a turn it moves to review; a person moves it to done. A session that errors marks the card failed.
- **"Run" is in memory only,** as in v1, so opening a repo never starts a fleet by itself.
- **Board changes travel as `board` frames**, not session events; the file is the source of truth.
- **Built-in ask rules** protect `.loom/policy.json` and the hub policy from edits without a person, whatever the policy files say.

## Verified with real Claude in the browser (2026-09-12)

A demo git repository with five cards (four Claude chat cards on Haiku, two of them supervised, one terminal card), all with worktrees, run with a cap of five:

- Five worktrees on five `loom/<title>-<id>` branches appeared under the hub's data directory; the repository's own checkout stayed clean.
- Three cards reached review on their own; the two supervised ones showed edit approvals from two sessions in the approvals panel, both allowed with the `a` key, and then reached review.
- Each worktree held only its own card's change, including two sessions that edited `math.js` at the same time.
- Marking a card done persisted to `.loom/board.json`; the run stopped itself when the to-do lane was empty.
- Archiving the terminal card's session with worktree removal deleted the directory and kept the branch; the same action on a session with uncommitted changes was refused with the reason.
- The overview showed four sessions with their latest activity and $0.16 spent today.

## Found and fixed during verification

- **Board unreachable:** a project's board could only be opened from its sessions; the overview now has an "Open board" field.
- **Stale client state:** the store merged objects from the hub instead of replacing them, so a cleared run cap stayed on screen and, on reconnect, approvals resolved in the meantime could linger. It now uses `reconcile`.
- **Menu closed early:** the session menu closed on mouse leave, which broke its two-step "remove worktree" confirm; it now closes on outside click or Escape.
- **Blocking dialogs:** the first draft used `window.prompt` and `window.confirm`; replaced with inline controls before verification (v1 lesson).
