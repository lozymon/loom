# WebSocket JSON frames, token auth, SSH and Tailscale before a relay

**Status:** Accepted (2026-09-12). Replaces v1's LAN bridge (`lanbridge.rs`, `lansec.rs`) and defers v1 ADR-0012's relay.

v1 shipped a home-grown ChaCha20-Poly1305 channel that was never independently reviewed. v2 should not own cryptography.

## Decision

- **Transport:** WebSocket, one JSON frame per message, validated with zod on both ends (`parseClientFrame`, `parseHubFrame`).
- **Frames:** client sends `hello` then `req`; hub sends `welcome`, `res` (one per req), and `evt` (ordered by seq). `PROTOCOL_VERSION` must match or the hub refuses.
- **Local:** the desktop connects over a unix socket (named pipe on Windows) with no token; OS user is the trust boundary, as in v1.
- **TCP:** requires a bearer token generated by the hub on first run, shown once, stored in the client's keychain. The hub binds to localhost by default.
- **Remote, in order:**
  1. SSH port forward managed by the desktop app.
  2. Tailscale: the hub binds to its tailnet address.
  3. Later (M11): the hub dials out over TLS to a relay on the user's VPS. No inbound port needed, which matters behind WSL NAT and corporate firewalls.
- No custom cryptography at any tier; TLS or SSH or WireGuard carry confidentiality.

## Consequences

- The browser client and the desktop client speak the same protocol.
- A `cli` and `mcp` client kind exist so the `loom` CLI and the Cockpit's MCP server are ordinary clients.
- Binding to anything other than localhost or a tailnet address is a warning in the UI.

## As built (M7, 2026-09-12)

- **Bind rules** (`hub/src/remote/network.ts`): `bind` is loopback (default), `"tailscale"` (resolved with `tailscale ip -4`), an address in 100.64.0.0/10 or fd7a:115c:a1e0::/48, or anything else only with `allowUnencryptedNetwork: true`, which prints a warning. The hub refuses to start otherwise. With a tailnet or LAN address it listens on loopback too, so hooks and local tools keep working; the startup link is printed for every address.
- **Hooks only from loopback:** `/hooks/<session>` answers 403 to any non-loopback caller; engines always run on the hub's machine.
- **Login limit** (`remote/loginLimiter.ts`): 10 bad tokens within 10 minutes blocks that remote address for 10 minutes, loopback included. A good token clears the count.
- **SSH** is `loom tunnel <[user@]host>` (`remote/tunnel.ts`), not the desktop app yet: `ssh -N -L 127.0.0.1:<local>:127.0.0.1:<port>` with `ExitOnForwardFailure` and keep-alives. It probes the new `GET /loom.json` (unauthenticated, returns only `{loom, protocol}`) to tell "hub up" from "forward up, no hub" and reconnects with backoff after a drop. If ssh exits before the forward ever opened, it stops instead of retrying. The default local port is the remote port plus 10000, so a local hub on 7420 does not collide. The M9 desktop app will reuse this module.
- **Clients hold several hubs** (`client/src/hub/registry.ts`, `hubList.ts`): addresses and tokens in local storage (the keychain comes with M9), deduplicated by the hub id from `welcome`.
- **Not done here:** the local unix socket or named pipe without a token (still TCP plus token everywhere); a UI warning for unencrypted binds (the hub prints it at startup only).

## Addendum (M10, 2026-09-13): HTTPS for phones

- Phones need https to install the PWA, use the microphone, and get push. Two ways, neither with Loom crypto:
  - **`tailscale serve`** in front of the hub's loopback port (recommended; certificates are Tailscale's). Behind a local proxy the hub takes the client address from `X-Forwarded-For` for the login limit, and refuses `/hooks` for any forwarded request.
  - **`tls: { cert, key }` in `hub.json`**, for example files from `tailscale cert`. The hub serves HTTPS on its network address and keeps loopback plain HTTP for hooks and local tools, which cannot check a certificate for 127.0.0.1. With `tls`, a LAN address no longer needs `allowUnencryptedNetwork`; a wildcard bind is refused.
- **Web push** (RFC 8291 encryption, RFC 8292 VAPID) is done by the `web-push` library. The hub's VAPID key pair lives in `push.json` in its data folder, mode 0600. Pushed text is the approval's one-line summary, never tool input.

## Addendum (M11, 2026-09-13): the relay

The third tier is built as TLS passthrough through a relay the hub dials out to, with the hub's own certificate from Let's Encrypt. See ADR-0014.
